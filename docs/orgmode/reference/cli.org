#+TITLE: CLI Reference
#+OPTIONS: toc:t num:t

* Top-level usage

#+begin_src text
nimvault {SUBCMD} [sub-command options & parameters]
#+end_src

nimvault auto-detects the git repository root via ~git rev-parse --show-toplevel~
and uses ~.vault/~ within it. All commands accept the optional ~--recipient KEY~
flag.

The CLI is built on [[https://github.com/c-blake/cligen][cligen]] with ~dispatchMulti~ for subcommand routing. Each
subcommand is a thin wrapper around the corresponding ~commands~ module proc.

* Commands

** seal

#+begin_src text
nimvault seal [--recipient KEY] [--force] [--public-only] [--noninteractive]
#+end_src

Encrypt every entry whose plaintext changed, and write the manifest.

Only changed files are re-encrypted. Encryption output is not deterministic --
both backends draw a fresh session key per run -- so re-encrypting an untouched
file would still produce a different blob, and a one-file edit used to arrive as
a diff touching every blob in the vault. An entry is skipped when its plaintext
hash, its blob, and that blob's own hash all still agree with the manifest, so a
deleted or corrupted blob is rebuilt rather than skipped.

A seal that changed nothing does not rewrite the manifest either. The manifest is
encrypted and signed, so writing it is a change in its own right.

Everything is re-encrypted regardless when the seal key changes, which covers the
backend, recipient, identity and signer: unchanged plaintext still owes a fresh
blob under a new key.

New ciphertext is written to ~<id>.gpg.pending~ (or ~.age.pending~). The record
is updated to name that file, and only then is it renamed over the live blob.
A crash before the record is durable leaves the previous blob in place. A
crash after the record is written leaves ~.pending~, which the next read
promotes when its hash matches.

Exits non-zero if any plaintext file is missing.

A public-key writer (~--public-only~, ~NIMVAULT_PUBLIC_ONLY=1~, or a gpg home
with no secret key) does not decrypt the vault. ~add~ already sealed the new
entry. ~seal~ reports that existing records were left untouched.

*** ~--force~

Re-encrypt every entry, not only the changed ones. Ignored for a public-key
writer, which cannot read the entries it would re-encrypt.

*** ~--public-only~

Append without a secret key. Do not read the manifest.

*** ~--noninteractive~

Fail instead of prompting. See [[file:../howto/machine-writers.org][machine writers]].

** unseal

#+begin_src text
nimvault unseal [PATH...] [--recipient KEY] [--allow-unsigned] [--vault DIR]
#+end_src

With no path this restores the whole vault. Naming paths restores only
those entries, and a directory restores everything beneath it. A selector
that matches nothing is an error.

Before decryption, verifies:
- Manifest GPG signature
- Blob SHA-256 hashes against manifest
- Path safety (no directory traversal)

Decryption writes to temporary files first. Only after all signatures and hashes
pass does the tool move files to their final paths. This atomic approach prevents
release of unverified plaintext under the final name.

The temporary file is =.nimvault-<id>.tmp= in the destination's directory,
mode 0600. It sits beside the destination so the final step is a ~rename~ on
one filesystem, which replaces a symlink at the destination instead of
writing through it. The cost: plaintext sits in that directory for the length
of the batch, before its in-band signature is checked when the blob carries
one, and a kill before the rename leaves it behind. ~nimvault gc~ shreds such
files.

Creates parent directories as needed. Sets file permissions to 600 (owner
read/write only).

Exits non-zero if:
- Any blob file is missing
- Any blob hash does not match the manifest
- Any signature is invalid or missing (unless ~--allow-unsigned~)
- Any target path escapes the expected boundary

*** ~--allow-unsigned~

Accept unsigned v1 vaults. Skips signature and hash verification. Bad signatures
(~BADSIG~) are still fatal even with this flag. Use this only for migrating
legacy vaults created before v0.2.0. Run ~nimvault seal~ afterwards to upgrade
the vault to signed v2 format.

An unadopted fragment under ~.vault/a/~ is not written unless this flag is
passed. A fragment whose path matches a signed record is refused even with
the flag. ~nimvault adopt~ signs that fragment into ~.vault/e/~.

** add-dir

#+begin_src text
nimvault add-dir <directory> [--recipient KEY] [--no-gitignore] [--public-only] [--noninteractive]
#+end_src

Add a directory recursively to the vault. Walks the directory tree and adds each
file individually with its own encrypted blob. The directory structure is
preserved via the relative paths stored in the manifest.

Each file undergoes the same checks as ~nimvault add~:
- With a secret key, verifies the file is not already in the vault. A
  public-key add cannot see existing entries.
- Checks ~git ls-files~ to ensure the file is not tracked by git
- Appends to ~.gitignore~ unless ~--no-gitignore~ is passed

Use ~add-dir~ for directories like ~.beads~, ~.env~, or any folder containing
multiple sensitive files.

Exits non-zero if:
- The directory does not exist
- The directory is empty
- Any file is already in the vault
- Any file is tracked by git

** add

#+begin_src text
nimvault add <path> [--recipient KEY] [--no-gitignore] [--public-only] [--noninteractive]
#+end_src

Add a file to the vault. The path is stored with =~/= for portability. Generates
a random 16-char hex ID, encrypts the file, computes a SHA-256 blob
hash, and appends a record.

With a secret key the record is signed under ~.vault/e/~. With public keys
only it is an unsigned fragment under ~.vault/a/~, encrypted to the wrap-rule
recipients, and the existing records are not decrypted. See
[[file:../howto/machine-writers.org][machine writers]].

Checks ~git ls-files~ to verify the file is not already tracked by git. If the
file is tracked, exits with an error instructing the user to untrack it first.

Appends one ~.gitignore~ line for that path. The line is anchored at the
repository root and ~#~, ~*~ and ~?~ are escaped, so the line matches the
file and not a comment or a glob. ~--no-gitignore~ skips the line. A path
that is already ignored is left alone.

Exits non-zero if:
- The file does not exist
- The file is already in the vault (needs a secret key to see that)
- The file is tracked by git
- The matching wrap rule names no recipient

** rm

#+begin_src text
nimvault rm <path> [--recipient KEY]
#+end_src

Remove a file from the vault. Deletes the encrypted blob and removes the
manifest entry. Does NOT delete the local plaintext file.

** mv

#+begin_src text
nimvault mv <old-path> <new-path> [--recipient KEY]
#+end_src

Move/rename a vault entry's target path. If the file exists at the old path, it
is physically moved. The encrypted blob is unchanged; only the manifest entry is
updated.

** adopt

#+begin_src text
nimvault adopt [PATH...] [--recipient KEY] [--noninteractive]
#+end_src

Sign unadopted ~.vault/a/~ fragments into ~.vault/e/~ and delete the fragments.
Needs a secret key. With no path, every openable fragment is signed. A fragment
whose path matches a signed record is refused and left unsigned. A fragment
whose path fails the traversal check is refused the same way.

** get

#+begin_src text
nimvault get <path> [--allow-unsigned]
#+end_src

Print one entry's plaintext on stdout without unsealing the vault or writing
the plaintext to disk, including the runtime directory. Applies the same
path-safety and blob-integrity checks ~unseal~ does. Deliberately quiet, so
nothing decorative shares the stream with a secret.

An unadopted ~.vault/a/~ fragment is refused unless ~--allow-unsigned~ is
passed. When a signed record names the same path, ~get~ returns that record.

** check

#+begin_src text
nimvault check [--recipient KEY] [--json] [--public-only] [--digests FILE] [--write-digests FILE] [--noninteractive]
#+end_src

Compare payload blobs to the records, or to ~.vault/blob-index~ when this
process has no secret key. Neither comparison decrypts a payload. Exit 2 when
anything is inconsistent, so a pre-push hook or a CI job can gate on it.

With a secret key the anchor is the manifest. The hashes live in the encrypted
records, so ~check~ decrypts those records and does not decrypt the payloads.
A public key alone cannot open the records. A missing blob, a hash that does
not match, a v1 entry with no hash, and a payload id that is not in the records
are problems. Without a secret key the anchor is the blob-index (id and
ciphertext sha256, no paths): added, changed and missing ids. If there is no
index and no digest list, and ciphertext exists, that itself is a problem.

~--digests FILE~ diffs a previous snapshot of every file under ~.vault/~
except ~config~ and ~*.tmp~. A delta exits 2, including an intentional add.
~--write-digests FILE~ writes that snapshot of the bytes on disk.
~--json~ prints one object: ~ok~, ~keyless~, ~anchor~, ~checked~, ~problems~,
and ~manifest~ / ~digests~ objects with ~added~, ~changed~, ~missing~.

This answers a different question from ~status~. ~status~ compares the
*plaintext* on this machine against the manifest, so it says nothing about
whether the blobs still match; a blob committed without the record that
vouches for it looks healthy there right up until an ~unseal~ somewhere else.

** gc

#+begin_src text
nimvault gc [--recipient KEY] [--dry-run]
#+end_src

Remove blobs in ~.vault/~ that no manifest entry points at.

Orphans are reachable when a mutation is interrupted between writing a blob and
writing the manifest that names it. The vault lock makes that rarer but does not
remove the case. An orphan is not only clutter: it is a readable copy of a
secret that nothing tracks, so nothing will ever rotate or remove it.

Never touches the manifest, the data-key files, or any blob a live entry names.
A ~.pending~ file whose hash a record names is kept, and so is one whose record
this machine cannot open. Any other ~.pending~ file is removed, as are
=<id>.gpg.tmp= and =<id>.gpg.pending.tmp= payloads a killed ~add~ or ~seal~ was
still writing.

~gc~ also shreds =.nimvault-<id>.tmp= files beside the entries this machine
can open. Those are plaintext an interrupted ~unseal~ staged; see ~unseal~.

*** ~--dry-run~

List what would be removed and remove nothing.

** rotate

#+begin_src text
nimvault rotate [--recipient KEY] [--rekey]
#+end_src

Rewrap the per-file data keys to whoever ~.vault/config~ now names. Payloads are
untouched, so adding a machine costs one small file rather than a full
re-encrypt.

That rotates the *wrapping* only: a recipient key that should no longer open the
vault stops being able to. It does nothing about a data key that has already
leaked, because the old ciphertext is unchanged and the old key still opens it.

*** ~--rekey~

Re-encrypt every payload under a fresh data key. This is the form that answers a
suspected compromise of a data key or of the plaintext, and the only one that
does. Churn is the intent, so it bypasses the incremental skip.

** scan

#+begin_src text
nimvault scan [PATH] [--cached | --rev REV [--remote NAME]] [--vault DIR]
#+end_src

Look for plaintext secrets that are not in the vault. With no flag, walk
~PATH~ (default: the current directory). A directory named ~tmp~ or ~log~ in
the repository is scanned. The same names under ~.claude~ or ~.codex~ are not.

~--cached~ reads the git index. ~--rev REV~ reads blobs introduced by a
commit (that commit and its ancestors) or by an ~A..B~ range, including a
secret added and then removed before the tip. A vaulted path in the index or
in those commits is reported even when its bytes do not match a pattern.
~.vault/~ itself is not scanned. ~--remote NAME~ leaves out commits that
~NAME~'s remote-tracking refs already reach. A commit in ~REV~ that this clone
does not have is an error that says to fetch first.

The pattern list skips binaries, files over 2MB, lines over 2000 characters,
and dependency directories on a worktree walk. It does not print the matching
line.

** list

#+begin_src text
nimvault list [--recipient KEY]
#+end_src

List all vault entries showing their ID and target path.

** status

#+begin_src text
nimvault status [--recipient KEY] [--json] [--noninteractive]
#+end_src

Show sync status of all vault entries by comparing local plaintext SHA-256
to the manifest ~contentHash~. Only v3-and-earlier entries that lack a
content hash are decrypted:

- ~[in-sync]~ :: local matches vault
- ~[modified]~ :: local differs from vault (needs ~seal~)
- ~[missing]~ :: local file not found (needs ~unseal~)
- ~[no-blob]~ :: encrypted blob missing (needs ~seal~ or ~add~)

Directory entries: When you ~add-dir~ a directory, each file appears individually
in ~list~ and ~status~ output. The directory structure is implicit in the paths.

** who

#+begin_src text
nimvault who [PATH...] [--recipient KEY] [--vault DIR] [--json] [--noninteractive]
#+end_src

Print the path, the recipients and the wrap rule (~recipient~ when the
configured recipient is the fallback).

Naming paths answers the rule from ~.vault/config~ and needs no secret key.
With no path, list the entries this identity can open.

** lock

#+begin_src text
nimvault lock [--recipient KEY] [--vault DIR]
#+end_src

Remove in-sync plaintext. Vault entries stay; ~unseal~ restores them. A
modified file is refused. A missing or mismatched blob is refused too: lock
does not delete the only remaining copy. The file is overwritten before it
is unlinked. Editor backups beside it (=name~=, =#name#=, =.name.swp=) are
removed the same way, and only when the file itself is present and in sync.
A symlink is unlinked and not followed. Records are verified as ~unseal~
verifies them, and a record path that fails the traversal check is refused.

** init

#+begin_src text
nimvault init [--recipient KEY] [--vault DIR]
#+end_src

Write ~.vault/config~ with the recipient. Refuses if the file already exists.

** hook

#+begin_src text
nimvault hook [--vault DIR]
#+end_src

Install a ~pre-commit~ hook that runs ~nimvault scan --cached~ and a
~pre-push~ hook that runs ~nimvault scan --rev~ on the commits being pushed,
then ~nimvault check~. Pushing to a named remote scans only commits that
remote's tracking refs do not reach, so a new branch is not refused for
history the remote already has. A push to a bare URL scans the whole range.
When the remote holds commits this clone has not fetched, the hook refuses
and says to run ~git fetch~. Refuses to overwrite existing hooks. Hooks
already installed keep their previous script until they are replaced by hand.

** doctor

#+begin_src text
nimvault doctor [--recipient KEY] [--vault DIR] [--json] [--public-only] [--noninteractive]
#+end_src

Print backend, recipient, binaries, manifest and ~check~ status. Exits 2
when something will not work. ~--json~ is one object with ~ok~, ~vault~,
~backend~, ~recipient~, ~gpg~, ~age~, ~manifest~, ~append~ and ~problems~.

* Where the vault lives

Every command accepts ~--vault DIR~. The vault repository need not be the one
you are standing in, which is what lets ~.vault/~ sit in a private repository
while the dotfiles it protects stay public. Resolution order:

1. ~--vault DIR~
2. ~NIMVAULT_VAULT_REPO~
3. a ~.nimvault~ pointer file in the current repository, naming the vault one
4. the current git repository

See the [[file:../howto/private-vault-repo.org][private vault repository how-to]].

* Global options

- ~--recipient KEY~ :: GPG recipient key ID. Overrides env var and config file.
  See [[file:config.org][configuration]] for the full resolution chain.
- ~--help~ :: Show help for the current command.
- ~--version~ :: Show nimvault version.

* Exit codes

| Code | Meaning                                                                 |
|------+-------------------------------------------------------------------------|
|    0 | Success                                                                 |
|    1 | Operational error (missing file, GPG failure, integrity check, traversal) |
|    2 | ~check~ or ~doctor~ found an inconsistency                              |
|    3 | Non-interactive run would have prompted, or no secret key to read entries |

* Security model

Signed records under ~.vault/e/~ are the trust root. A public-key fragment
under ~.vault/a/~ is encrypted to the recipients and not signed; a missing or
bad signature on ~.vault/e/~ is still fatal. On ~unseal~, signatures and
blob hashes are verified before any plaintext is written to disk:

1. Manifest signature is checked during decryption, and must come from a key
   the config names (see [[file:config.org][configuration]])
2. Blob SHA-256 hashes are compared against the manifest
3. Target paths are validated against directory traversal
4. Blobs are decrypted to temporary files
5. Signatures are verified on each blob that carries one in band. gpg blobs
   encrypted to a recipient do; age blobs and v6 enveloped blobs do not, and
   take the same guarantee from the signed manifest plus the digest checked at
   step 2
6. Only after all checks pass are files moved to their final paths

This design prevents forgery, ciphertext swapping, path traversal, and release
of unverified plaintext for the signed records. An unsigned ~.vault/a/~
fragment is not written by ~unseal~ or ~get~ unless ~--allow-unsigned~ is
passed, and a path that matches a signed record is refused even then.
~adopt~ signs the fragment into ~.vault/e/~.

** Known limitations

These are inherent trade-offs of Git-backed OpenPGP vaults, not bugs.

*** Metadata leakage

Because the tool encrypts files individually, an observer analyzing the Git
history can track update frequency, ciphertext size variations, and file count
over time. GPG ciphertext sizes correlate with plaintext sizes, so relative file
sizes are visible. Wrapping the entire payload in an archive before encryption
would conceal this metadata but sacrifice Git delta efficiency. For most personal
vault use cases this trade-off is acceptable.

*** No forward secrecy

An adversary who archives the public Git history today and obtains a key later
can decrypt every historical version. Git keeps the old ciphertext whatever the
current vault holds, so no operation on the working tree reaches it.

Be careful which rotation is meant here. ~nimvault rotate~ rewraps the data keys
to new recipients and leaves payloads alone, so it does nothing for an archived
copy: the old blobs and the old data keys are both still in history.
~rotate --rekey~ re-encrypts the payloads, which changes what is stored *from
now on* but does not reach back either. Only rewriting the history removes the
old ciphertext, and only a private remote avoids the archiving in the first
place.

The distinction between rewrapping a key and re-encrypting the data it protects
is treated formally in Everspaugh et al., CRYPTO 2017
([[https://doi.org/10.1007/978-3-319-63697-9_4][doi:10.1007/978-3-319-63697-9_4]]).
