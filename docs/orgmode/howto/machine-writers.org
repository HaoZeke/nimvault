#+TITLE: Machine writers
#+OPTIONS: toc:t num:nil

A writer is often a CI runner that holds recipient public keys and no secret
key. It can append entries and it can check ciphertext. Reading an existing
entry still needs a secret key for one of that entry's recipients.

* Public keys only

Signing a record needs a secret key. ~.vault/e/<id>.gpg~ stays signed, and a
missing or bad signature there is still fatal. A home with no secret key, or
~--public-only~ / ~NIMVAULT_PUBLIC_ONLY=1~, does not open those records.

~add~ and ~add-dir~ then write three things and leave the rest of the vault
alone:

- ~.vault/<id>.gpg~ or ~.age~ -- the payload, under a fresh data key
- ~.vault/a/<id>.gpg~ or ~.age~ -- the path, the hashes and the data key,
  encrypted to the wrap-rule recipients, not signed
- one line in ~.vault/blob-index~ -- the id and the ciphertext sha256, no path

~seal~ in this mode does not decrypt anything. It reports that the sealed
records were left untouched. It does not treat an unreadable vault as empty,
so it does not delete key files.

The filename is inside the fragment, not in the blob name. ~.gitignore~ still
lists an in-repo plaintext path, as it does for any other add.

A public-key writer cannot see paths already in the vault, so a second
fragment can name the same path. Resealing an edited existing entry needs a
secret key. An older binary ignores ~.vault/a/~.

gpg does this when the home has no secret key. age does it when the
identity file is absent, because that file is the decrypt key and the ssh
key is only the signer. ~--public-only~ forces the lane even when a decrypt
key is on disk.

* What a signature proves

A signature on ~.vault/e/~ proves the long-term signing key produced that
ciphertext. gpg checks it while decrypting, so a runner with no secret key
cannot. An age ssh signature verifies with the public allowed-signers file,
and the payload digest is still inside the ciphertext.

The fragment under ~.vault/a/~ is not signed. A key minted for that one run
would prove only that the process which encrypted the fragment could also
sign it. Anyone holding the recipient public key can do that, so it is not
used. Keyless integrity is the plaintext digest list: ~check --digests~
compares ciphertext bytes with a list written earlier. It does not say who
wrote them.

Anyone who has the recipient public keys can plant a fragment. ~unseal~ and
~get~ do not write that plaintext unless ~--allow-unsigned~ is passed. A
fragment whose path matches a signed record is refused even then. ~nimvault
adopt~ is the step a holder of the secret key uses: it signs the fragment
into ~.vault/e/~ and deletes it. A colliding path is refused there too.
~check --digests~, taken from outside the change, is what shows the
ciphertext without a key. ~rotate~ (the rewrap, not ~--rekey~) signs every
openable fragment that does not collide with a signed path. ~seal~, including
the ~rotate --rekey~ path, leaves fragments where they are.

#+begin_src yaml
- name: Append with public keys only
  env:
    NIMVAULT_PUBLIC_ONLY: "1"
    NIMVAULT_NONINTERACTIVE: "1"
  run: |
    nimvault add personas/mosswell/note.txt
    nimvault seal
#+end_src

The job's ~GNUPGHOME~ has imported the recipient public keys and holds no
secret key.

* Recipients by path

The first matching ~wrap~ rule decides. An entry matching none uses
~recipient~.

#+begin_src ini
recipient = OWNER
wrap = personas/mosswell/**:MOSSWELL,OWNER
wrap = **:OWNER
#+end_src

~personas/mosswell/**~ matches paths under that directory and seals them to
that persona and the owner. ~**~ is the fallback for everything else.

A rule that matches and names no recipient fails before any file is written.
The entry is not silently sealed to ~recipient~.

#+begin_src text
FATAL: wrap rule 'personas/mosswell/**' matches personas/mosswell/note.txt but names no recipient
#+end_src

~nimvault who PATH~ prints ~path~, the recipients, and the glob. That reads
the config only. With no path, ~who~ lists the entries this identity can
open, which decrypts records.

#+begin_src yaml
- name: Show the wrap rule for one path
  run: nimvault who --json personas/mosswell/note.txt
#+end_src

* Non-interactive

~--noninteractive~ or ~NIMVAULT_NONINTERACTIVE=1~ adds ~--pinentry-mode error~
to gpg encrypt, decrypt and sign. A prompt, a missing secret key, or a
cancelled pinentry exits 3. Other failures stay 1. The symmetric data-key
passphrase still goes in on a file descriptor (~--pinentry-mode loopback~);
that path does not open a prompt.

~status~, ~who~, ~check~ and ~doctor~ take ~--json~ and print one object on
stdout. ~status~ and ~who~ print ~{"ok":false,"error":"..."}~ when they fail
before that object. ~check~ and ~doctor~ print their own object and exit 2
when ~ok~ is false.

| Code | Meaning |
|------+---------|
| 0 | Success |
| 1 | Operational error |
| 2 | ~check~ or ~doctor~ found an inconsistency |
| 3 | Would have prompted, or a public-key writer tried to read sealed entries |

~status~, and ~who~ with no path, need a secret key once the vault has
records. ~who PATH~, ~add~, ~seal~, ~check~ and ~doctor~ do not.

#+begin_src yaml
- name: Status as JSON, no pinentry
  env:
    NIMVAULT_NONINTERACTIVE: "1"
  run: nimvault status --json
#+end_src

* Check without a key

With a secret key, ~check~ compares each blob to the hash in the records it
can open. A missing blob, a hash mismatch, and a payload id that is not in
those records are all problems.

Without a decrypt key (no gpg secret key, or no age identity file) it does
not decrypt records. It compares top-level
~.vault/<16 hex>.gpg~ (and ~.age~) files to ~.vault/blob-index~.
~keys.<group>.gpg~ is not a payload.

#+begin_src text
# nimvault-blob-index-v1
0123456789abcdef 9f2b...
#+end_src

Added, changed and missing ids are problems. If ciphertext exists and there
is no index and no ~--digests~ file, the problem is ~no blob-index and no
digest list; cannot check without a key~.

~--write-digests FILE~ writes every file under ~.vault/~ except ~config~ and
~*.tmp~, including the blob-index. The file is the bytes on disk, even when
the check is already dirty.

#+begin_src text
# nimvault-digests-v1
a/0123456789abcdef.gpg 9f2b...
blob-index abcd...
#+end_src

~--digests FILE~ diffs that snapshot. Any added, changed or missing path is a
problem and the exit is 2. A new entry that is in the blob-index is
internally consistent, and it still fails a comparison with an older
snapshot. Write the list after a clean seal. Pass ~--digests~ to detect
drift from that snapshot, not from a list rewritten in the same change.
~--json~ puts the id lists under ~manifest~ and the path lists under
~digests~. ~anchor~ is ~manifest~, ~blob-index~, ~digests~ or ~none~.

#+begin_src yaml
- name: Fail if ciphertext drifted
  env:
    NIMVAULT_NONINTERACTIVE: "1"
  run: nimvault check --json --public-only --digests nimvault-digests.txt
#+end_src
