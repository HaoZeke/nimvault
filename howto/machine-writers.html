Machine writers¶

Contents

  • Machine writers

    • Public keys only

    • Recipients by path

    • Non-interactive

A writer is often a CI runner that holds recipient public keys and no secret key. It can append entries and it can check ciphertext. Reading an existing entry still needs a secret key for one of that entry’s recipients.

Public keys only¶

Signing a record needs a secret key. .vault/e/<id>.gpg stays signed, and a missing or bad signature there is still fatal. A home with no secret key, or --public-only / NIMVAULT_PUBLIC_ONLY=1, does not open those records.

add and add-dir then write three things and leave the rest of the vault alone:

  • .vault/<id>.gpg or .age – the payload, under a fresh data key

  • .vault/a/<id>.gpg or .age – the path, the hashes and the data key, encrypted to the wrap-rule recipients, not signed

  • one line in .vault/blob-index – the id and the ciphertext sha256, no path

seal in this mode does not decrypt anything. It reports that the sealed records were left untouched. It does not treat an unreadable vault as empty, so it does not delete key files.

The filename is inside the fragment, not in the blob name. .gitignore still lists an in-repo plaintext path, as it does for any other add.

A public-key writer cannot see paths already in the vault, so a second fragment can name the same path. Resealing an edited existing entry needs a secret key. An older binary ignores .vault/a/.

gpg does this when the home has no secret key. age does it when the identity file is absent, because that file is the decrypt key and the ssh key is only the signer. --public-only forces the lane even when a decrypt key is on disk.

What a signature proves¶

A signature on .vault/e/ proves the long-term signing key produced that ciphertext. gpg checks it while decrypting, so a runner with no secret key cannot. An age ssh signature verifies with the public allowed-signers file, and the payload digest is still inside the ciphertext.

The fragment under .vault/a/ is not signed. A key minted for that one run would prove only that the process which encrypted the fragment could also sign it. Anyone holding the recipient public key can do that, so it is not used. The same person can rewrite .vault/blob-index, which is unsigned and carries no paths. A keyless check that matches the blob-index detects accidental drift only: a blob edited or deleted outside nimvault. It does not say who wrote an entry, and it does not see a plant that updated the index. check --digests against a snapshot taken outside that change is the tamper signal.

A keyed reader does not trust an unsigned fragment while signing is required. check fails. get and unseal skip the fragment and warn. rotate --adopt rewrites a fragment that does not duplicate a signed id or path as a signed .vault/e/ record. seal does not adopt one. A duplicate path or id across e/ and a/ is never trusted: the signed entry wins, and check keeps failing until that fragment is gone.

- name: Append with public keys only
  env:
    NIMVAULT_PUBLIC_ONLY: "1"
    NIMVAULT_NONINTERACTIVE: "1"
  run: |
    nimvault add personas/mosswell/note.txt
    nimvault seal

The job’s GNUPGHOME has imported the recipient public keys and holds no secret key.

Recipients by path¶

The first matching wrap rule decides. An entry matching none uses recipient.

recipient = OWNER
wrap = personas/mosswell/**:MOSSWELL,OWNER
wrap = **:OWNER

personas/mosswell/** matches paths under that directory and seals them to that persona and the owner. \*\* is the fallback for everything else.

A rule that matches and names no recipient fails before any file is written. The entry is not silently sealed to recipient.

FATAL: wrap rule 'personas/mosswell/**' matches personas/mosswell/note.txt but names no recipient

nimvault who PATH prints path, the recipients, and the glob. That reads the config only. With no path, who lists the entries this identity can open, which decrypts records.

- name: Show the wrap rule for one path
  run: nimvault who --json personas/mosswell/note.txt

Non-interactive¶

--noninteractive or NIMVAULT_NONINTERACTIVE=1 adds --pinentry-mode error to gpg encrypt, decrypt and sign. A prompt, a missing secret key, or a cancelled pinentry exits 3. Other failures stay 1. The symmetric data-key passphrase still goes in on a file descriptor (--pinentry-mode loopback); that path does not open a prompt.

status, who, check and doctor take --json and print one object on stdout. status and who print {"ok":false,"error":"..."} when they fail before that object. check and doctor print their own object and exit 2 when ok is false.

Code

Meaning

0

Success

1

Operational error

2

check or doctor found an inconsistency

3

Would have prompted, or a public-key writer tried to read sealed entries

status, and who with no path, need a secret key once the vault has records. who PATH, add, seal, check and doctor do not.

- name: Status as JSON, no pinentry
  env:
    NIMVAULT_NONINTERACTIVE: "1"
  run: nimvault status --json

Check without a key¶

With a secret key, check compares each blob to the hash in the records it can open. A missing blob, a hash mismatch, a payload id that is not in those records, and an unsigned .vault/a/ fragment are all problems. get and unseal skip that fragment until rotate --adopt.

A missing decrypt key does not enter the keyless comparison by itself. On a signer-configured vault that is a failure, unless --public-only (or NIMVAULT_PUBLIC_ONLY=1) was set. With that flag, check does not decrypt records. It compares top-level .vault/<16 hex>.gpg (and .age) files to .vault/blob-index. keys.<group>.gpg is not a payload. The index is unsigned and writable by the same public writer, so this comparison is accidental drift only. Pass --digests for a tamper check.

# nimvault-blob-index-v1
0123456789abcdef 9f2b...

Added, changed and missing ids are problems. If ciphertext exists and there is no index and no --digests file, the problem is no blob-index and no digest list; cannot check without a key. If the blob-index and the records are both gone but a manifest or data-key file remains, that is not an empty vault: check fails unless --digests is passed, which is what a CI job needs in order to pass.

--write-digests FILE writes every file under .vault/ except config and \*.tmp, including the blob-index. The file is the bytes on disk, even when the check is already dirty.

# nimvault-digests-v1
a/0123456789abcdef.gpg 9f2b...
blob-index abcd...

--digests FILE diffs that snapshot. Any added, changed or missing path is a problem and the exit is 2. A new entry that is in the blob-index is internally consistent, and it still fails a comparison with an older snapshot. Write the list after a clean seal. Pass --digests to detect drift from that snapshot, not from a list rewritten in the same change. --json puts the id lists under manifest and the path lists under digests. anchor is manifest, blob-index, digests or none.

- name: Fail if ciphertext drifted
  env:
    NIMVAULT_NONINTERACTIVE: "1"
  run: nimvault check --json --public-only --digests nimvault-digests.txt
