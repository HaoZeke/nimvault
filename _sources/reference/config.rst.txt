=============
Configuration
=============


.. contents::


1 Recipient resolution
----------------------

nimvault resolves the GPG recipient through a 3-tier chain. The first non-empty
value wins:

1. **CLI flag**: ``--recipient KEY`` (or ``-r KEY``)

2. **Environment variable**: ``NIMVAULT_GPG_RECIPIENT``

3. **Config file**: ``.vault/config`` in the git repository root

If none are set, nimvault exits with an error.

.. image:: ../images/recipient_resolution.svg

2 Config file format
--------------------

``.vault/config`` uses a simple key-value format:

.. code:: ini

    # Lines starting with # are comments
    recipient = 9CCCE36402CB49A6
    root = repo

Whitespace around the ``=`` is ignored. Recognized keys:

``recipient``
    GPG key ID for encryption (required).

``root``
    Base directory for path resolution. When set to ``repo``, paths are
    stored relative to the repository root. When set to a relative path, it is
    resolved against the repository root. When absent, paths use ``~/`` prefix for
    portability.

``wrap``
    Repeatable. ``<glob>:<recipient>[,<recipient>...]`` -- which
    recipients may open the entries matching a path pattern. See below.

``backend``
    ``gpg`` (default) or ``age``. Also ``NIMVAULT_BACKEND``. Any other
    value is refused.

``identity``
    Age identity file. Also ``NIMVAULT_AGE_IDENTITY``.

``signer``
    ``gpg`` (default for the GPG backend), ``ssh`` (default for age),
    or ``none``. Any other value is refused, and so is ``gpg`` with ``backend = age``:
    gpg signs only what it encrypts, so it would sign and verify nothing. With
    ``none``, ``unseal`` and ``get`` need ``--allow-unsigned``.

``sign_key``
    SSH private key used to sign the manifest when ``signer = ssh``.

``allowed_signers``
    SSH allowed-signers file used to verify that signature.

``signer_identity``
    Principal to match inside ``allowed_signers``.

2.1 The config is trusted as written
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``.vault/config`` is plaintext, committed and unsigned. The ``recipient`` and
``wrap`` lines decide who may sign records and who the next ``seal`` encrypts to;
``allowed_signers`` and ``signer_identity`` decide whose ssh signature verifies.
Whoever can change the file can change who may sign and who can read. Review
a diff to it as you would review code, before the next ``unseal`` or ``seal``.
See the `threat model <../explanation/threat-model.rst>`_.

3 Per-path recipients
---------------------

Not every machine should read every secret. A ``wrap`` rule maps a path pattern
to the recipients allowed to open those entries:

.. code:: ini

    recipient = laptop@example.com

    # Specific rules first: the first match decides.
    wrap = ~/.ssh/**:laptop@example.com
    wrap = ~/.gnupg/**:laptop@example.com
    wrap = **:laptop@example.com,buildbox@example.com

Order in the file is precedence, so the narrow rules go above the general one.
An entry matching no rule uses ``recipient``, which is why a config with no
``wrap`` lines behaves exactly as it did before rules existed.

3.1 How it works
~~~~~~~~~~~~~~~~

Each entry's payload is encrypted under its own data key (see the manifest
reference). The data keys are grouped by recipient set, and each group is
written to its own ``.vault/keys.<group>.gpg`` encrypted to that group alone. A
machine decrypts the group files its key opens and no others, so it can read
exactly the entries meant for it.

``unseal`` on such a machine restores what it can read. ``check`` compares
payload blobs with the recorded digests and does not decrypt the payloads.
The digests are stored in the encrypted records.

Patterns: ``\*`` matches within one path segment, ``\*\*`` spans separators, and a
pattern ending in ``/`` covers everything beneath it. Patterns are anchored at
both ends, so ``~/x/*`` does not match ``~/x/deep/one``.

3.2 Changing the rules
~~~~~~~~~~~~~~~~~~~~~~

Editing ``wrap`` rules does not move anything by itself. Run ``nimvault rotate``:
it recomputes each entry's group and rewrites the key files, leaving payloads
untouched. An entry that moved group has its key written to the new group's
file and dropped from the old one.

3.3 A prerequisite worth stating
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Groups are only worth anything when the machines hold **different** keys. If
every machine shares one private key, every machine can open every group and
the split is decoration. Give each machine its own key and exchange public
keys before relying on this.

3.4 Break-glass recovery
~~~~~~~~~~~~~~~~~~~~~~~~

Because a group takes several recipients, an offline key -- generated once,
printed or kept on removable media, never on any machine -- can be added to
the general rule. It then opens the vault if every machine is lost, without a
threshold scheme or any additional machinery.

4 GPG key ID
------------

The recipient, and each recipient in a ``wrap`` rule, must name a key
exactly:

- Long key ID: ``9CCCE36402CB49A6``

- Fingerprint: ``ABCD1234...``

- Email: ``user@example.com`` or ``<user@example.com>``

- Subkey ID or fingerprint, optionally with gpg's trailing ``!``. The key it
  belongs to is the one allowed to sign.

- 8-hex short key IDs are refused.

Any other string, such as a name, is refused when the config loads, whether
it comes from ``.vault/config``, ``--recipient`` or ``NIMVAULT_GPG_RECIPIENT``. gpg
matches such a string anywhere in a user ID, so ``Alice`` also names
``Malice <malice@example.com>``, and that key could then sign records.

Use a 16-hex key ID or a full fingerprint when naming keys by hex.

4.1 Who may sign
~~~~~~~~~~~~~~~~

With ``signer = gpg``, a record or blob verifies only when gpg reports a good
signature whose primary key is one the config names: ``recipient`` or a
recipient in a ``wrap`` rule. A good signature from any other key in the
keyring is refused. ``add`` and ``seal`` sign with an allowed key explicitly
(``--local-user``). If this machine has no allowed secret key, they fail.

This signer set is vault-wide. Any configured recipient (base ``recipient`` or a
recipient listed in any ``wrap`` rule) can sign records for any path in the
vault. ``wrap`` controls **decryption scope** only; it does not scope who may sign
which path. Per-glob signer scoping is a known limit.

So a key named only in a ``wrap`` rule can write every path. In the example
above, the build box can sign a record for ``~/.bashrc`` or
``~/.ssh/authorized_keys``, and the laptop writes it on the next ``unseal``. Name
a machine in a ``wrap`` rule only if you would let it write those files.

An email spec is matched as an exact address (``<user@example.com>``), and
matches every key in the keyring that carries that exact email. Use a
fingerprint or long key ID when another key with the same email could be
imported.

4.2 Finding your key ID
~~~~~~~~~~~~~~~~~~~~~~~

.. code:: bash

    gpg --list-keys --keyid-format long
    # pub   rsa4096/9CCCE36402CB49A6 2024-01-01 [SC]
    #                ^^^^^^^^^^^^^^^^ this is the key ID
